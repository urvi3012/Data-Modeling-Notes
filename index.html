Data Modeling & Engineering

Data modeling is the process of defining the structure, relationships, and constraints of data. In Data Engineering, modeling is the link between raw transaction systems and clean, analytical insights. Without a model, data is just a pile of numbers; with a model, it is a business asset.

The Modeling Phases

  • Conceptual Model: High-level overview of business entities (e.g., Customer, Order). Focuses on "What" data exists.
  • Logical Model: Defines structural logic, keys, and relationships. Database-agnostic.
  • Physical Model: The technical implementation. Includes data types, indexes, and partitioning for a specific DB.

1. OLTP vs. OLAP

OLTP (Online Transactional Processing)

Designed for the "Front-end." OLTP systems handle thousands of fast, small transactions (e.g., swiping a credit card). They use Normalization to prevent data duplication and ensure integrity.

OLAP (Online Analytical Processing)

Designed for the "Back-end." OLAP systems aggregate millions of records for analysis (e.g., "Monthly revenue per region"). They use Denormalization to optimize for massive read scans.

Criterion OLTP (Operational) OLAP (Analytical)
PurposeProcessing transactions (Run the business).Data Analysis (Understand the business).
Data FormatNormalized (3NF) to save space/ensure integrity.Denormalized (Dimensional) to speed up reads.
ArchitectureSource systems (ER modeling).Target systems (Dimensional modeling).
PerformanceOptimized for fast, frequent writes.Optimized for bulk read scans.
RequirementsACID compliance, high availability.Query speed, historical scalability.
ExamplesPostgreSQL (Recording a bank deposit).Snowflake (Analyzing year-over-year growth).

3. Facts & Dimensions (Gold Layer)

Fact Tables (Measures)

Store quantitative numbers and foreign keys. Usually "Long and Thin."

  • Transactional: One row per event (A single sale).
  • Accumulating Snapshot: Tracks a process (Order → Ship → Deliver).

Dimension Tables (Context)

Store descriptive attributes (Who, What, Where). Usually "Short and Wide."

  • Conformed: Shared across multiple facts (Universal Date table).
  • Role-Playing: One table used twice in a fact (Order Date vs Ship Date).

4. Surrogate Keys

A Surrogate Key is an artificial, system-generated primary key (usually an integer 1, 2, 3) used instead of a natural key (like Email or SSN).

  • Speed: Joining on integers is faster than strings.
  • Stability: It doesn't break if a user changes their email.
  • History: Essential for SCD Type 2 tracking.

5. Star vs. Snowflake Schema

Star Schema: All dimensions connect directly to a central fact. Fastest read performance, easy for BI tools to understand.

Snowflake Schema: Dimensions are normalized into sub-dimensions (e.g., Product → Category). Saves space but slows queries due to more joins.
