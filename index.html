Data Modeling for Engineers

Why do we model data? In source systems (Apps), we care about writing data fast. In Data Engineering, we care about reading data fast for analytics. Data modeling is the bridge that transforms messy, operational records into clean, business-ready insights.

1. The Starting Point: OLTP vs OLAP

OLTP (Online Transactional Processing)

Designed for the "Front-end." When a user clicks 'Buy', the database needs to record that single row instantly. It uses Normalization to prevent data duplication. If a user changes their name, it changes in one place.

OLAP (Online Analytical Processing)

Designed for the "Back-end." When a CEO asks 'Total sales by region', the database needs to scan millions of rows. It uses Denormalization to reduce joins and speed up massive calculations.

3. From OBT to Dimensional Gold

In the Silver Layer, we often create One Big Table (OBT). This is a massive table where all source joins (User + Order + Product) are already done.

Why OBT? It’s easy for data scientists to query. However, for large scale BI, we divide this OBT into the Gold Layer (Fact and Dimension tables).

  • Fact Tables: Contain the "Quantitative" data (metrics, numbers).
  • Dimension Tables: Contain the "Qualitative" data (who, what, where).

4. Types of Facts & Dimensions

Fact Table Types

  • Transactional: One row per event (e.g., A single sale).
  • Periodic Snapshot: Summarizes data over a period (e.g., Monthly bank balance).
  • Accumulating Snapshot: Tracks a process with a start and end (e.g., Order -> Shipped -> Delivered).

Dimension Table Types

  • Conformed: A dimension used by multiple facts (e.g., A "Date" table shared by Sales and Inventory).
  • Role-Playing: One table used for multiple purposes (e.g., "Date" table acts as both "Order Date" and "Ship Date").

6. The Surrogate Key

A Surrogate Key is a system-generated unique identifier (usually an integer like 1, 2, 3) that acts as the Primary Key in a dimension table.

Why not use Natural Keys (Email/ID)? If a user changes their email, your foreign keys in the Fact table won't break. It also makes joins significantly faster than joining on long strings.
